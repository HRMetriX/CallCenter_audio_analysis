# CallCenter Audio Analysis Pipeline

Пайплайн для расшифровки двухканальных записей телефонных разговоров call-центра (стерео OGG, 8 кГц) с диаризацией и пословными таймстампами. Результат предназначен для последующего NLP-анализа.

## Особенности

- **Независимые каналы.** Запись обрабатывается по каналам отдельно: канал 0 — сторона колл-центра (оператор), канал 1 — клиент. Корреляция каналов на тестовой выборке около 0, утечка между ними ниже -35 дБ, поэтому joint-диаризация не нужна.
- **Диаризация на Pyannote.** Детекция речи по каждому каналу через `pyannote/speaker-diarization-3.1`. Silero VAD и RMS-эвристики не используются: они теряли тихого оператора после IVR.
- **Единая частота 16 кГц.** Файл декодируется один раз в родном SR (8 кГц), затем каждый канал ресемплится в 16 кГц через `soxr`. Весь дальнейший пайплайн (диаризация, нарезка, ASR) работает на 16 кГц.
- **Посегментная ASR.** Каждый речевой сегмент вырезается и транскрибируется GigaAM v3 e2e RNNT отдельно. Это снижает галлюцинации на паузах и позволяет ловить короткие реплики.
- **Подготовка сегментов.** Близкие сегменты одного канала (пауза < 0.6 с) склеиваются, пока спан не превысит 23 с, вокруг каждого добавляется паддинг ±0.25 с, перед ASR применяется локальная нормализация громкости с ограничением усиления +30 дБ.
- **Длинные монологи.** Обычный `transcribe` GigaAM принимает до ~25 с. Сегменты длиннее 24.5 с (с учётом паддинга) не режутся по времени, а обрабатываются через `transcribe_longform` (режет по паузам собственным VAD, пословные таймстампы сохраняются). Такие реплики получают флаг `longform`.
- **Ошибки ASR не теряются молча.** Упавший сегмент остаётся в `dialogue.json` с флагом `asr_error` и пустым текстом, счётчики `asr_errors` и `longform_segments` пишутся в статистику канала.
- **Короткие звуки.** Речь короче 0.25 с в ASR не отправляется и помечается `[короткий звук]` (флаг `short_sound`).
- **Пословная разметка.** Таймстампы слов приведены к абсолютному времени записи.
- **Перебивания.** Реплики обоих каналов объединяются в один список и сортируются по `start`.
- **Контроль согласованности SR.** Если длина вырезанного буфера не совпадает с ожидаемой длительностью, обработка файла прерывается с ошибкой, а не выдаёт мусорный текст.
- **Идемпотентность.** Готовые файлы при перезапуске пропускаются и не перезаписываются. Источник истины — папки результатов в `data/out/`, а `processed_files.json` самовосстанавливающийся индекс (подробнее в разделе «Реестр и повторные запуски»).
- **Защита от потерь.** Результаты пишутся атомарно, `transcript.json` последним; lock-файл не даёт запустить два экземпляра одновременно.

> Обработка идёт in-memory, кроме одного шага: для вызова GigaAM каждый сегмент временно записывается в WAV, который удаляется сразу после распознавания.

## Технологический стек

- Python 3.10+
- GigaAM v3 e2e RNNT (ASR)
- Pyannote Audio (диаризация, требуется `HF_TOKEN`)
- soxr (ресемплинг)
- ffmpeg / ffprobe (декодирование и метаданные)
- PyTorch, NumPy, SoundFile

## Установка

1. Клонируйте репозиторий:
   ```
   git clone https://github.com/HRMetriX/CallCenter_audio_analysis.git
   cd CallCenter_audio_analysis
   ```

2. Установите зависимости:
   ```
   poetry install
   ```
   Убедитесь, что в зависимостях есть `soxr` и `pyannote.audio` (при необходимости: `poetry add soxr`).

3. Убедитесь, что `ffmpeg` и `ffprobe` установлены и доступны в PATH.

4. **Windows, для `transcribe_longform`:** нужна shared-сборка FFmpeg (с DLL), иначе `torchcodec` не загрузится (`Could not load libtorchcodec`). Например:
   ```
   winget install --id Gyan.FFmpeg.Shared -e
   ```
   Версия FFmpeg должна поддерживаться вашей версией `torchcodec` (4–9), а пара `torch`/`torchcodec` должна быть совместима (см. таблицу в репозитории torchcodec).

5. Создайте файл `.env` в корне проекта (шаблон: `.env.example`):
   ```
   HF_TOKEN=ваш_токен_huggingface
   FFMPEG_DLL_DIR=C:\путь\к\ffmpeg-shared\bin
   ```
   Токену нужен доступ к моделям Pyannote (нужно принять условия использования на странице модели на Hugging Face). `FFMPEG_DLL_DIR` нужна только на Windows; `main.py` добавляет эту папку через `os.add_dll_directory` до импорта моделей.

## Использование

Обработка одного файла:
```
poetry run python main.py --file data/in/call_recording.ogg
```

Пакетная обработка папки:
```
poetry run python main.py --dir data/in
```

Тестовая выборка из N случайных файлов (выбирается только из необработанных):
```
poetry run python main.py --dir data/in --random 5
```

Повторная обработка файлов, в которых были сегменты с ошибкой ASR (`asr_errors > 0`):
```
poetry run python main.py --dir data/in --retry-errors
```

Переобработать **все** файлы, даже готовые (результаты перезаписываются, реестр не стирается):
```
poetry run python main.py --dir data/in --force
```

Обычный перезапуск без флагов безопасен: готовые файлы пропускаются, а если все файлы готовы, модели даже не загружаются.

## Реестр и повторные запуски

- **Файл считается обработанным**, если в `data/out/<имя>/` есть `<имя>_transcript.json`. Он записывается последним (после `dialogue.json` и `readable.json`), поэтому обрыв посреди обработки не создаёт «наполовину готовый» результат: такой файл будет обработан заново.
- **`processed_files.json`** — индекс с метаданными (время обработки, длительность, `asr_errors`, версия пайплайна). При каждом запуске он сверяется с `data/out/`: записи без результатов удаляются, результаты без записи добавляются. Если реестр потерян или повреждён, он восстанавливается сам; старые форматы реестра (список файлов) тоже читаются.
- **`failed_files.json`** — файлы, упавшие с исключением (текст ошибки, число попыток). Они не попадают в реестр и повторяются при следующем запуске.
- **`.pipeline.lock`** — lock с PID: второй экземпляр пайплайна не стартует, пока жив первый. Устаревший lock (процесса уже нет) удаляется автоматически.
- **Начать с нуля:** переименуйте `data/out` (например, в `data/out_old`) и запустите снова — реестр сам обнулится по результатам.

Все эти файлы (`processed_files.json`, `failed_files.json`, `.pipeline.lock`) добавлены в `.gitignore`.

## Структура выходных данных

Результаты сохраняются в `data/out/<имя_файла>/`:

| Файл | Содержимое |
|---|---|
| `<name>_transcript.json` | Полная статистика по каналам, пословная транскрипция, метаданные (исходный SR, длительность, флаги). |
| `<name>_dialogue.json` | Хронологический список реплик с таймстампами, полями `speaker`, `channel`, `words`, `flags`. |
| `<name>_readable.json` | Диалог для чтения: подряд идущие реплики одного спикера склеены. Поля `turns` (со временем) и `lines` (строки вида `оператор: ...`, `клиент: ...`). |

Пример `<name>_readable.json`:
```json
{
  "source_file": "123.ogg",
  "duration_sec": 184.2,
  "turns": [
    {"speaker": "operator", "start": 0.5, "end": 6.1, "text": "Здравствуйте, компания ..."},
    {"speaker": "client", "start": 6.4, "end": 9.0, "text": "Добрый день, я по поводу заказа"}
  ],
  "lines": [
    "оператор: Здравствуйте, компания ...",
    "клиент: Добрый день, я по поводу заказа"
  ]
}
```

В `readable.json` не попадают реплики `[короткий звук]`, они же не разрывают реплику собеседника. Короткие бэкканалы («угу», «да»), успешно распознанные ASR, реплику разрывают.

## Известные ограничения

- **Роли каналов заданы жёстко:** `ch0 = operator`, `ch1 = client`. На тестовой выборке из 20 файлов порядок каналов оказался обратным в 3 случаях, в них подписи ролей будут перепутаны.
- **IVR-робот не выделен.** Речь робота в начале записи попадает в реплики оператора (канал 0) и может искажать NLP-аналитику. Клиент может говорить поверх робота на своём канале.
- **Молчащий клиент.** Если клиентский канал пуст (в части файлов активность канала 0%), файл обрабатывается как обычно, отдельного флага пока нет.
- **Longform зависит от окружения.** Требует `HF_TOKEN`, shared-сборку FFmpeg и совместимые `torch`/`torchcodec`. Без них длинные сегменты вернут `asr_error` (пайплайн не упадёт, но реплика будет пустой). Внутренний VAD longform может отбросить очень тихую речь, на таких репликах стоит выборочно сверить текст.
- **Нет оценки уверенности ASR.** Автоматической фильтрации галлюцинаций нет; качество оценивается вручную на выборке.

## Облегчение пайплайна (план экспериментов)

Это гипотезы для проверки, а не реализованные решения. Скорость и качество на ваших данных нужно замерять.

### Что избыточно

Полная диаризация `speaker-diarization-3.1` кластеризует голоса, но в двухканальной записи на канале говорит один человек. Нужна только детекция речи по каналу, а эмбеддинги и кластеризация лишние.

### Варианты замены детектора речи (от лёгкого к тяжёлому)

1. **Silero VAD по каждому каналу.** Лёгкая модель, быстро работает на CPU. Раньше от неё отказались из-за потери тихого оператора после IVR, но тот эксперимент мог быть искажён ошибкой с SR (8 кГц в WAV с заголовком 16 кГц), поэтому вывод нужно перепроверить. Против потери тихой речи помогает нормализация громкости по окнам перед VAD.
2. **Pyannote `segmentation-3.0` без кластеризации** (`VoiceActivityDetection`). Тот же сегментатор без эмбеддингов, заметно быстрее полной диаризации.
3. **Текущая диаризация 3.1.** Оставляем, если варианты 1–2 проигрывают по качеству.

### Другие ускорения

- Пропускать детекцию и ASR для молчащего клиентского канала и ставить флаг `client_silent`.
- Передавать аудио в GigaAM из памяти, если API это позволяет, вместо временных WAV.
- Обрабатывать файлы параллельно в нескольких процессах, если хватает памяти GPU.

### Порядок проверки

1. Замерить время по этапам (декодирование, диаризация, ASR) на 3–4 файлах. Если основное время уходит на ASR, замена детектора мало что даст.
2. Реализовать детектор речи с тем же интерфейсом, что у `SpeakerDiarizer.diarize_channel`, чтобы заменить модуль без правок в `pipeline.py`.
3. Прогнать те же файлы с теми же параметрами слияния и паддинга.
4. Сравнить с текущим выводом: потерянные реплики (особенно тихого оператора), число мусорных сегментов, расхождение текста, время обработки.
5. При равном качестве выбрать более быстрый вариант.
